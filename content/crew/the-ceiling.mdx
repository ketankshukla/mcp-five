Project #3's agent handles one cookie jar beautifully. So project #4 gave it a
pantry: **sixty jars**, each needing its own inspection, one jar per tool call,
each report about 250 tokens of seal state, weights, notes and movement log.
Nine have been tampered with, and the rule for spotting one has two clauses and
an exception.

At sixty jars, it just… did it. Perfectly. Four iterations, every jar
inspected, all nine found, nothing innocent touched.

<Callout type="insight" title="Which was not the expected result, and that is worth saying">
  The premise — *"sixty verbose reports is too much for one context window"* —
  was simply **wrong**. It is about 15,000 tokens, and the model batched the
  inspections twenty at a time.

  A finding that kills your premise on stage 5 is a good outcome. The honest
  move is to stop asserting where the ceiling is and go and find it.
</Callout>

So the pantry got a dial, and it was turned up to 240.

<Callout type="quote">
  A failing agent is expensive precisely because it fails slowly.
</Callout>

## You cannot fix this with a better prompt

Because it is not a prompt problem. It is a **shape** problem.

And the mechanism is not the one people usually reach for. It is not that the
task is too hard, or that the model gets confused, or that 240 is too many
things to hold in mind.

<Callout type="lesson" title="The single agent fails expensively because it re-sends everything it has read on every iteration">
  All 240 inspection reports ride along in the conversation, growing every trip
  around the loop.

  Its **cost grows with the square of the job while its capacity stays fixed.**
  It runs out of iterations long before it runs out of things to inspect, and
  it has paid full price for every re-read along the way.

  This is [The meter](/learn/host/the-meter)'s superlinear-cost observation,
  arriving with a bill attached.
</Callout>

## The kitchen

A head chef does not cook faster. They do something different: split the work,
hand pieces to other cooks, and keep only the **plan** in their own head
instead of every detail. The details live with whoever is doing that piece.

<Callout type="insight" title="And the reason the crew gets further is structural, not motivational">
  It is not that three agents are somehow smarter.

  **Each worker gets its own fresh context and its own fresh ten-iteration
  budget.** Three workers with ten iterations each is thirty iterations of
  capacity where one agent had ten — and none of them is carrying the other
  two's jar reports around.
</Callout>

## How solid are these numbers?

Stated plainly, because the honest version of this table is more useful than
the tidy one.

| Row | Confidence |
|---|---|
| **60 jars, accuracy** | Solid. Three attempts per case, both modes, 100% in both — 6/6 one agent, 12/12 crew. |
| **60 jars, cost** | The softest number here. Two attempts of the one case both modes run identically; the run-to-run spread (85k–99k single, 74k–83k crew) is a meaningful fraction of the gap. **"A wash"** is as strong a claim as the data supports. |
| **240 jars** | A single attempt per mode, plus a standalone probe that independently agreed. The direction is not in doubt — one mode finished and the other emptied nothing — but treat the magnitudes as one significant figure. |

The compare run and the standalone probe give slightly different totals
(440,517 / 245,948 versus 439k / 248k). Both are real; they are different runs.
This site quotes the probe figures because those are the ones the source
README's headline table uses.

<Callout type="warning" title="And the first version of this comparison was wrong">
  It said the crew cost **1.7×** at 60 jars and concluded "delegation is pure
  overhead." Every individual number in that report was accurate. The division
  was the lie.

  That story is [The measurement trap](/learn/crew/measurement-trap), and it is
  the most useful page in this section.
</Callout>

## The crossover is a property of your job

Not of agents in general. It depends on how big each tool result is, how many
calls the job needs, and how tight your iteration cap is.

So the useful skill is not *"know that delegation is good."* It is **knowing
how to find your own crossover** — which is a script you can run, not an
opinion you can hold:

```bash
npm run compare -- --attempts 5
PANTRY_JARS=240 npm run compare
```
