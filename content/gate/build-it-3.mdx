## The checkpoints, in order

Each proves one layer before the next is stacked on it, so you are never more
than one layer away from a bug. The first two cost nothing.

```bash
npm run mcp:list        # 1. can we reach the servers?        (no AI)
npm run mcp:translate   # 2. do schemas convert? what's gated? (no AI)
npm run agent           # 3. does the loop chain its output?
npm run approval        # 4. THE GATE — approve AND deny
npm run evals           # 5. the report card
npm run replay          # 6. the rewind button
```

## The two tools that lie to you

Project #3's appendix has eight entries. These two are the ones worth
memorising, because in both cases **the tool tells you something false with a
confident face.**

<Callout type="gotcha" title="1 — `git check-ignore -v` lies about negations">
  You add `!.env.example` to un-ignore a file. You check your work:

  ```bash
  git check-ignore -v .env.example
  ```

  It prints a matching line and exits **0**. Exit 0 reads like "yes, ignored" —
  so you conclude the negation didn't work and start editing `.gitignore`
  again.

  It is actually reporting *which pattern matched*, and the pattern it matched
  is your negation. The file is fine.

  **Use `git add -n <file>` instead.** It tells you what git will actually do:

  ```bash
  git add -n .env.example
  # add '.env.example'          ← it will be added
  # or: "The following paths are ignored by one of your .gitignore files"
  ```

  This one bit project #3 *and* project #4, which is how it earned a place in
  two appendices.
</Callout>

<Callout type="gotcha" title="2 — the dev server that would not die">
  You Ctrl-C the shell. You close the terminal. The port is still in use, and
  your "restarted" server is the old one with the old `.env.local`.

  Killing the shell that started a dev server does not kill the server. Check
  the **port**, not the shell:

  ```bash
  Get-NetTCPConnection -LocalPort 3000 -State Listen
  ```

  Three projects hit this — #2, #3 and #4. When the same surprise recurs three
  times, the mental model is wrong, not the command: a process is not owned by
  the terminal you happened to launch it from.
</Callout>
